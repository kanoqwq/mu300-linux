# 在线缩容后的再次安装衔接

## 已确认的问题

F50 已免擦卸载并扩回 Android，随后再次保数据缩容 8 GiB。F2FS ioctl、
GPT 提交、重启后的 userdata 和解密映射均已成功，但安装器报
`Reclaimed space is not free`。扩容不承诺清零所有空闲块，重新回收的尾部
还残留旧 OpenWrt ext4 主超级块。通用空闲区扫描正确识别出签名，但在线
缩容流程缺少“这是本次已确认回收的 userdata 尾部”的交接处理。

这不是缩容失败，不需要重复 ioctl、清空 Android 或关闭所有签名检查。

## 公共修复

- GPT 扫描返回发现的文件系统类型和绝对扇区，普通未登记文件系统保护保持不变。
- 只在原、新 GPT 精确匹配已校验快照、设备身份与 Android 槽一致、原 F2FS
  UUID 保持、目标容量与重启后映射均通过验证后处理。
- 只有完整落在本次回收且用户已选择用于 OpenWrt 的范围内的签名允许清理。
  原先已存在的其他空闲区、越界签名、未知布局不参与自动处理。
- 每处保存并校验 8 KiB 原始头到本次电脑事务的 `online-shrink/reclaimed-headers`。
  写入前再次核对设备 boot ID、userdata 大小、两份 GPT 和原始头哈希，
  仅清理该头并回读；不改 GPT、现有 userdata、Android boot 或 NV。
- 断线后复用已保存记录。已完成的清理不重复执行；部分写入只接受各扇区与
  原备份相同或已清零，其他变化停止并保留现场。
- 完成后重新探测空闲区，再进入原有安装流程。不是通过忽略签名绕过检查。

两仓库使用同一实现，既有首次安装、明确格式化后备、TF、更新和卸载路径
不增加新的格式化步骤。

## 验证与边界

新增 `installer/tests/test_reclaimed_gap.py` 用真实 GPT 和稀疏普通文件执行
实际 shell 检查/清理命令，不操作测试主机的块设备：

1. eMMC 512-byte / UFS 4Kn、E5/MU300、ext4/F2FS 残留与多个签名。
2. 缩容后探测、清理、重新生成安装计划、协调器进入安装入口。
3. 写前断线、写后断线、部分写入、重新加载事务续接、不重复缩容。
4. 错误设备/槽/UUID/容量/GPT、越界签名、被修改备份及设备侧竞态拒绝。
5. 生产 Adapter 扫描器在清理前保护、清理后放行；通用保护仍生效。

全套后端测试：E5 452 项、MU300 415 项。Windows 分别跳过 84/88 项
POSIX 或环境限定项；Linux root 补跑后分别跳过 3/7 项平台限定项，适用项全部通过。
Linux 首次运行缺少 paramiko/lz4 并使用了无 chown 权限的用户，补齐依赖并
按所需权限重跑后通过；未把缺依赖的失败记为成功，也未修改测试来掩盖。

F50 当前失败事务已实机续接：原 UUID 保持，Android 16,395,534,336 字节，
回收 8,589,934,592 字节。仅在扇区 44,298,240 备份/清理旧 ext4 头；重新
规划与原确认计划一致，MU300 旧安装入口也确认该空间可用，事务恢复 ready。
本轮未执行后续完整系统写入，不能把这一结果称为全机型安装硬件验收。
