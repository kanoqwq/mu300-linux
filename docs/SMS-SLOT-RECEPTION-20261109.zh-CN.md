# 双槽短信接收归属修正（2026-11-09）

## 已确认问题

共享 NR0 的直投 +CMT 没有可靠的接收槽位标签。旧 mu300-modemd 以 broker
端口号选择短信池，smsd 再按该池导入并确认；来自槽位 1 的通知从 NR0
进入时，可能被归到槽位 0。这不是应该交换两个短信库或 IMEI 的理由。
Pro 与 MU300 的原生实现均有此缺口。E5 的双卡接收器已有明确存储查询来
确定归属；本轮补齐它对两槽通知模式的统一配置，避免主槽继承直投模式。

## 实现

- 沿用 E5 已采用的存储指示方式：每槽明确 SPACTCARD 后设置 PDU 和 CNMI
  存储通知；CSMS 设置后再次确认接收模式，避免初始化重置通知选项。
  Pro/MU300 同时指定 CPMS 的接收存储为 SM，与现有归档读取的存储一致；
  CSMS 拒绝本身不阻止可验证的存储收件，CNMI/PDU/存储失败则明确失败重试。
- NR0 的 +CMTI 只负责唤醒。两接收器经各自既有命令 owner/队列查询自己的
  存储，由实际 CMGL/CMGR 结果确定归属；不根据 NR0、当前上网槽、最后
  一条选卡命令、发送者或物理卡源猜测。
- 在配置通知与首次归档之前订阅既有事件，补上首次扫描到进入等待之间
  的通知窗口。没有新增常驻 AT 轮询；已有定期安全归档继续保留。
- 继续使用现有逐条原始 PDU 归档：先持久保存、导入并校验本地副本，再
  清理已核实的那个存储索引。满卡、读取不完整、索引变化、落盘或删除
  失败保留可恢复原件，不清空整卡。
- 未带可靠槽位信息的直接 CMT 存入独立 unassigned/incoming，不进入任一
  槽位库、不触发猜测性的 CNMA。重试的相同原始 PDU 用内容摘要去重，防止
  相同待确认数据无限堆积。旧 incoming 文件保留，不自动重标历史短信。
- 删除操作即使发现旧 direct marker，也只恢复存储指示模式，避免下一次
  手工删除又重新打开有歧义的直投路径。

- Pro/MU300 手动刷新也沿用同一 PDU 导入器，避免文本模式丢失长短信 UDH。
  首次归档明确标为历史，成功初始化后的新收取标为 stored-live；转发仍检查
  本地接收时间不得早于开启时间，但不因短信中心时间较早丢弃延迟到达的新短信。
  长短信只要含历史分段，合并结果仍按历史处理；不把历史补档整体升级为新消息。

## F50 Pro 边界

F50 Pro 的机身卡槽、内置卡与基带槽位并不总同号。短信只按逻辑槽位 0/1
查询和存储，不能按外置 SIM1/2 的印字改标签，也不能让板号改变收件池。
本轮没有改变其 GPIO、选卡、双待、预启动顺序、IMEI 或 NV。原有 F50 Pro
板号／双卡源组合回归与新接收流程分别执行，离线通过不替代 F50 Pro 实机。

## 特殊直投与验收边界

普通存储短信有明确的槽位证据。若厂商仍把 class-0 或其他不可存储消息以
无槽位 CMT 直投，现有通用接口不能凭空恢复接收槽；本轮只能保留原始 PDU，
不会假装已归属或已收件成功。此类私有扩展仍需真实接口证据才能自动归属。
不把这一限制藏成“所有消息都已验证”。不自动迁移之前误归属的历史记录。

规范依据仅用于解释标准 CMTI/CMT 的信息边界，不是厂商配置实测：
https://www.etsi.org/deliver/etsi_ts/127000_127099/127005/19.00.00_60/ts_127005v190000p.pdf

离线检查包括实际双接收器/原生导入、同一 NR0/发送者/PDU/索引分别落两槽、
持久化后再清理、旧直接帧保留、未知归属重试去重、空卡空转、事件监听断开、
真实 ucode/ubus 模拟通道与 F50 Pro 卡源组合。未主动发送真实短信或拨打电话。

## 本轮交付状态

修改落在正式 overlay 和既有编译/安装路径中，不要求安装 SIP 插件后才修正。
SIP 本身继续只读原生短信库，按槽位和独立游标派发，不新增调制解调器读取者。
已补充相同正文、相同本地编号来自两槽时的插件路由回归。

本轮只做离线检查，未把原生接收器热部署到机器，未重启基带或发送测试短信。
新的源码检查包含 LF/语法、收取/清理次序、通知、历史屏障、multipart 和事件 EOF；
F50 Pro 的 20 项原厂板号/卡源/预启动回放用例逐项通过，未改变这些硬件逻辑。
编译根校验会拒绝仍带旧接收脚本的 staging，不能把源码通过说成新包已打好。
