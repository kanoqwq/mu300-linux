# U30 Air 上电自启动：取消原厂加载器的版本白名单

## 确认的问题与适用范围

这里讨论的是网页充电管理中打开“上电自启动”，关机后插电启动，
不是普通电源键开机。原厂 charger 路径可能已启动 PM，却没有加载 NR/CH。

旧 `mu300-modem-coldboot` 只接受一个完整 `modem_control` 文件哈希，
再向两个固定偏移写指令。因此仅更换版本字符串或重新布局代码，都会
被视为不支持，导致 `android-vendor-start` 退出。这是已确认的源码缺陷。
没有取得反馈用户机器的实际日志，因此不能据此断言所有“6.18 上电自启动
无基带”都由这个缺陷造成。两条内核发行线共用本次用户态修复。

## 新的识别方式

新增 `tools/modem-loader/modem-loader-patch.c`，编译成无动态库依赖的
AArch64 静态程序。不调用 AT，不读取或写入 NV，不改 Android 的加载器。
同一辅助程序还支持 E5 的 ARM32/Thumb 文件；Thumb 的 9 字节比较通过
动态段和 PLT/GOT 重定位核实为 memcmp，不能仅凭一个相似字节串修改。

1. 校验 ELF64、小端、AArch64、程序头边界及映射，按虚拟地址映射到文件偏移。
2. 寻找完整调用路径：PM 已启动谓词 → 保存结果 → 解析 `modem` → 与
   `shutdown` 比较 → 合并 PM 谓词 → 条件跳过初次加载。
3. 核对谓词对 `/dev/sctl_pm` 的引用、cmdline 解析函数的实际引用，以及
   `load_modem_img` 的加载协议。三个不同的可写上下文必须有同一控制函数的
   停止／启动配对，分别受 bit0、bit5、NR 掩码 `0x0a` 控制。
4. 只接受唯一匹配的调用路径。在 RAM 副本中将 PM 谓词保存值改为零、
   初次加载掩码从 63 改为 34（NR/CH，保留已经运行的 PM）。
5. 写入后同步并逐字节回读整份副本；其余文件内容必须原样保留。
   输出不得是输入自身或符号链接。识别失败时不打开／截断目标文件。

这里的 63、34、加载位定义和指令语义是所识别协议的一部分，
不是固件版本号、文件哈希或文件地址。版本字符串、代码重定位、ELF
文件偏移、可匹配的寄存器和栈布局、NOP 填充变化不需要增加白名单。
如果编译器或厂商改成了另一套尚未核实的调用 ABI，识别器会说明不能
唯一核实；不能把取消版本白名单理解为允许向任意二进制盲写。

外层门控保持不变：仅 U30 Air、charger、`modem=shutdown` 且 CP 通道尚未
就绪时运行。正常开机、其他机型、CP 已就绪时继续使用原厂原文件，
不新增等待或重拨，不改 AT 所有权和回放顺序。

## 构建接入

`tools/modem-loader/build.py` 复用现有交叉编译器及固定的
`out/modem-loader/` 小型产物缓存，记录源码、构建器和二进制指纹。
没有新建内核、SDK 或 rootfs 缓存。

OpenWrt 的 `openwrt/build-rootfs.sh` 和 Ubuntu 的 `tools/make-release.sh` /
`rootfs/assemble.sh` 都构建并安装该程序。OpenWrt 两条内核发行线共用
这条路径；最终 rootfs 必需文件清单同时检查辅助程序，避免只带新脚本
却遗漏其依赖。辅助程序不需要重新编译内核。

## 离线验证

`tests/test_modem_loader.py` 包含独立构造的重定位 ELF，以及原厂样本的
可选精确结果校验。原厂二进制不纳入仓库或构建输入；测试通过
`MU300_COLD_LOADER_TEST_FILE` 显式提供。

覆盖不同虚拟／文件地址、寄存器／栈布局、NOP、不同版本字节、
逐条破坏启动路径、错误加载位及停止／启动配对、重复候选、缺失锚点、
截断／错误 ELF、源目标同文件和符号链接。拒绝路径必须保留原文件及
已有输出。`tests/test_charge_boot.py` 继续运行外层门控和原厂 RAM 副本测试。

已知原厂样本的两处修改与原来的精确回归结果一致。人工构造变体仅能
验证识别算法，不算其他固件版本的实机验收。本次没有刷写或重启实机。

同时清理通用 CPU adapter 的固件哈希捷径。所有 SML 版本都由已有
`sml-voltage-check` 根据实际 DVFS_INIT 和 CPU/SRAM 指令链识别。
原厂电压、持久化配置和一次性初始化顺序保持不变。
