# U30 Air Wi-Fi 断流日志与 PCIe 发送回收修正

## 现场证据

分析用户提供的 `logs.7z`，SHA256：
`2ef25176ddaebdc2e2e650b245155d2f8b61c8a8b09d69f98fafeeedde8e7e34a`。
原始文件仅保存在忽略的调查目录，不纳入仓库或发布。

报告注明 U30 Air、Linux 7.2.8，采集时开机约 23 小时；没有完整发布版本、
加载模块的 Build ID 和原厂 Android 固件版本，不能据此确认具体软件提交。
用户确认现象是热点仍可连接但无法上网，13:14 左右手动重启 Wi-Fi 后恢复。

- dmesg 覆盖 uptime 10129.973294–83735.732927，开头已处于运行阶段。
- EDMA 通道 10 暂满的可见累计拒收从 4623 增到 48688，返回 `-EAGAIN`。
  它是提交尝试计数，包含重试；不是丢包数，也不证明总线完全停止。
- 没有该窗口内的 WCN assert、Oops 或 watchdog 超时。仍可看到总线回调、
  beacon 更新及 SIPA 活动；这些不等于业务流量正常。
- 有客户端断连／重连和末段主动热点重启。日志中的 `del_station reason:2`
  出现在固件断连通知之后，不能将其当作固件报告的原始空口断开原因。
- SIPA `-EINPROGRESS` 有随后授予资源／唤醒队列的记录，不能将每次短暂
  资源请求都解释为基带卡死。采集后的单次接口统计也不能证明故障时进度。

## 已复现的代码缺陷

1. RX 收到 TXC 后先按通知数量减少 outstanding 计数、唤醒 TX，然后另行分配
   `SPRD_PCIE_TX_FREE_BUF` 工作项。此时发送缓冲尚未回收，额度已可用；
   若工作项分配失败，唯一的完成通知被丢弃，缓冲和消息持续占用。
2. `pcie_skb_to_tx_buf()` 失败时调用者仍继续复制 DMA 地址并提交，可能使用
   未准备好或残留的地址。
3. 旧回收按通知数量无条件扣减，且在核实 outstanding 所有权前使用固件
   回传地址解除映射；重复／未知完成不应制造额度或重复解除映射。

以上在实际生产 C 函数的离线夹具中复现。日志没有记录每项缺陷的触发现场，
因此目前将其视为明确代码缺陷和断流候选原因，不宣称已证明本次唯一根因。

## 修正

- 在现有 PCIe RX worker 内处理 TXC，去掉第二次工作项分配和提前发布额度。
  不是在 EDMA 硬中断中执行，不新增线程、定时重启或轮询。
- 对完成消息长度进行检查。按 outstanding 映射查找消息，使用与原映射
  相同的长度解除 DMA 映射，再归还缓冲和消息；只按真正回收的数量归还
  额度、更新计数和唤醒发送。
- 地址比较沿用厂商物理地址掩码，兼容完成通知保留或去除 MH 标记位。
  重复／未知地址不重复回收，不从未经核实的地址恢复消息指针。
- 检查 TX 缓冲准备结果；失败时释放本次地址 mbuf，原待发消息保留，
  已准备好的缓冲留给后续重试，不提交残留地址。
- 保留现有 pending ring 容量、固件额度、暂满事件唤醒、节能和 AT 所有权。

6.18/7.2 使用共享 `upstream/modules/sprd_wlan_combo`。5.4 的相同代码通过
`kernel/patches/wlan_combo-zz-pcie-txc-reclaim.patch` 进入既有有序 backport 链。
E5 的 SDIO 和 Pro 的 AIC8800 不能直接使用此 PCIe 修正。

## 验证

- 三项旧代码对照均以断言失败复现问题；修改后四项生产 C 测试通过，启用
  ASan/UBSan，覆盖分配失败、回收前后额度、重复／未知完成、消息长度及
  原始映射长度、MH 标记和调试时间戳。
- Wi-Fi 回归共 48 项：43 通过，5 项因未提供相应环境而跳过。
- 5.4 公共来源的四个相关文件按现有补丁顺序应用后，新增 backport 及
  同样四项 C 测试通过；没有宣称完成整个 5.4 内核构建。
- 6.18.54、7.2.8 的 WCN/WLAN 配套模块编译通过，任务记录：
  `out/build-logs/20261109-060133-wifi-txc-both-final-12448/`。
  正式交付缓存仍是登记的 `kernels/mu300-<version>`，不复制整份根文件系统。
- 未热部署、未重启任何设备；尚需群友同等使用负载下复测，不能将离线
  测试或编译通过称为断流实机验收。
