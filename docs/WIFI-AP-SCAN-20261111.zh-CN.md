# AP 开启时的客户端搜索调查

## 已确认的扫描生命周期问题

SC2355 `sc2355_scan()` 发送扫描命令失败后，旧实现调用
`sc2355_cancel_scan()`，向 cfg80211 提交完成事件，又返回启动失败。
这违反扫描请求的单一归属约定：失败返回应交回请求，接受的扫描才应通过
完成事件交回，不能两者同时进行。

另一个问题是发现已有扫描时只打印日志，继续运行会覆盖共享的
`scan_request` 和 `scan_vif`，丢失原有请求。

现在拒绝重入，保持原有请求和超时器。命令失败时取消超时器并在原锁下
仅清理本次请求，不发送完成事件；若固件完成事件／超时已先接管，则返回
接受，避免再以失败返回重复交回。所有完成路径的 `cfg80211_scan_info`
均初始化，防止把未初始化的 TSF 等字段交给内核。

AP、STA、第二 STA 仍使用已有扫描命令、固件版本协商和控制通道，没有
禁用 AP 扫描、临时关闭热点、强制重置 WCN 或修改固定信道。
源码位于两条 6.18／7.2 发行线共用的 `upstream/modules/sprd_wlan_combo`；
需要分别重新编译对应模块，不能拿一条内核的 ko 用于另一条。

## AP 接口返回 ACS，而不是附近热点

2026-11-11 在用户连接的 F50 上测试，运行内核 7.2.8，原发行版
`r20261110.153443-g71df27e0-s1bb1cb25`。原驱动与修正生命周期后的驱动
都能接收 AP 的扫描命令，但内核日志只报告 ACS 信道统计和 `0 BSSes`。
直接扫描 `wlan0` 返回空列表；这台机器没有复现用户报告的整机卡死。

实际创建一个未关联的 managed 接口后，可以发现附近 2.4/5 GHz 热点，
同时保留原 AP。因此为 LuCI 使用的 libiwinfo 增加明确的 SC2355 AP
扫描路径：识别 PHY 所属 `sprd_wlan_combo` 模块，创建本进程专有的
临时 STA，扫描后删除。不关联其他 AP、不关闭原热点、不重载 hostapd，
不更改信道、密码或用户无线设置；失败直接返回，不转入关闭 AP 的后备路径。
`NL80211_ATTR_SOCKET_OWNER` 让进程异常退出时由内核回收临时接口。

驱动识别必须读取 `/sys/class/net/<接口>/phy80211/device/driver/module`。
本机 netdev 的直接父设备是虚拟 misc 设备，直接读取 `device/driver`
会漏判。早期试验还受到已有 BSS 缓存干扰；最终验收同时观察了实际临时
接口创建及新收到的 beacon/probe response，不以非空缓存作为成功依据。

## 实机验证和构建接入

### 保持 AP 工作的约束

扫描不能关闭／重建原 AP、切换其信道、重启 hostapd/WCN 或覆盖无线配置。
临时扫描接口失败时只清理自己，不用关闭 AP 换取结果。单射频离信道扫描
仍可能短暂增加延迟；当前无关联客户端的接口保留验证，不等于已验收持续
流量、客户端不掉线或零吞吐损失。后续须在关联客户端下验证这些指标。

AP＋STA 同时关联是独立能力：当前 `sprd_iface_limits` 把 STATION 与 AP
放在同一个 `.max = 1` 分组，不能把声明的“三接口、两信道”理解为支持
普通 AP＋STA。未关联临时 STA 扫描成功也不是并发上网证据。必须进一步
核对固件及同信道关联行为，不直接提高接口数量来宣称支持。
若后续支持无线中继，还需区分路由/NAT 中继与需要上级兼容的透明二层桥接。

- 修正后的 LuCI `ubus iwinfo scan` 连续 5 次返回 11、11、11、11、12 个
  热点，每次约 2.3 秒；内核记录了实际临时接口扫描及新 BSS。
- 强制杀死独立扫描测试进程，确认临时接口自动删除，原 AP 保留；随后
  `device=radio0` 的 LuCI 扫描再次成功。
- AP 的 ifindex、MAC、36 信道/80 MHz 和设备 boot ID 保持不变，无新增
  panic/Oops。无线配置 SHA-256 前后相同。没有测试关联客户端持续吞吐。
- 新 WLAN 模块从 `/tmp` 热加载，磁盘原 ko 未替换；重启会恢复原模块。
  修正版 libiwinfo 则通过本地 APK 安装，并重启 rpcd 使之生效。
- 没有重启整机、修改启动分区、操作 NV/IMEI 或改变基带配置。

原始证据保留于忽略目录 `work/f50-ap-scan-20261111/`，其中最终验收使用
`final-phy-luci-*`、`phy-library-owned-scan.json`、
`interrupted-scan-phy-confirmed.json` 和 `final-device-health.txt`。
目录含设备信息及附近热点，不作为公开构建输入。

`openwrt/build-iwinfo-ap-scan.sh` 复用既有 OpenWrt SDK，构建已固定源码的
`libiwinfo20230701` APK。`tools/build-layout.json` 登记缓存路径，发布前验证
源码指纹和 APK 校验和；rootfs 路径安装该包及构建标识。没有新增常驻进程。

7.2 WLAN 模块与用户态库已经编译；6.18 共用的驱动源码已修正，但本轮
没有重新编译或实测 6.18，也没有生成完整发行包。后续打包需分别构建匹配
内核的模块。U30 Air 的整机卡死及 AP/STA 关联热切换仍需相应实机验收。

## 离线验证与未确认部分

`tests/test_wifi_scan_lifecycle.py` 编译执行真实扫描入口和取消函数，覆盖
三种接口模式下成功、拒绝、完成事件先到、重复请求。负向夹具恢复旧的
拒绝与完成并行行为，验证它不能满足归属约定；不依赖 Git HEAD 的内容。

这是可确定的代码缺陷，不是对用户“扫描整机卡死”的实机根因定论。
当前没有故障堆栈、WCN assert、固件版本协商或扫描拒绝原始回复；若新
模块下仍能复现，需要在该现场继续区分命令超时、固件异常和接收路径。
E5 使用较新的 SC2355 基线，CMD_SCAN 声明版本为 3，MU300 为 2；不能
因为 E5 可以扫描就直接提高 MU300 的协议版本。本轮未改变该声明。

`tests/test_iwinfo_ap_scan.py` 编译执行真实临时接口管理函数，覆盖创建失败、
名称冲突、MAC/启动/扫描失败及成功清理，并验证补丁重复应用和 PHY 驱动识别。
