# U30 Pro：安装后 Logo 转黑屏

2026-11-02，MU5358 原厂 Android B，Linux A；首次 preview1 安装到
`mu300root` 容器。在线 F2FS 缩容的几何误判另见安装器
`docs/F2FS-PARTIAL-SECTION.zh-CN.md`，不是此次启动问题。

## 实际证据

- 安装记录、设备 SHA-256 和电脑生成的 boot/vendor_boot/init_boot/dtbo 一致。
  Android B 的 boot 未变，BSP 两槽一致，不存在漏写启动镜像的证据。
- 本机 uboot_log 记录新内核大小 `0x1133008`，加载到 `0x80628000`，
  最后跳到该 Linux 入口，FDT 在 `0x86000000`。AVB 的返回 5 在原厂
  Android 正常启动也存在，不能据此归因 AVB 拦截。
- 失败后根 ext4 的 mount_count=0，最后挂载点和时间仍是 Android 安装器，
  尚未完成 Linux 根挂载；没有获取到该次 Linux 的 pstore 日志。
- 原 init 在启动后只执行一次设备节点扫描，立即找 misc 和根分区。
  MMC 的异步枚举尚未完成时缺少这些节点，没有等待或可用的失败控制台。
- 另一明确缺陷：USB configfs helper 在成功绑定 UDC 后还调用 UCI 修改
  uhttpd；initramfs 没有 UCI，set -e/EXIT 清理会撤销已建立的 USB gadget。

## 修正及实机结果

启动时轮询本机内部盘及本模式必需分区，逐次刷新 PARTNAME 别名；设备已就绪
则立即继续，不设置固定启动延时。最多等待 10 秒，不选择其他盘或写 GPT。
根挂载失败保留明确阶段日志，并尝试提供 NCM/ACM 救援控制台。
USB helper 保留配置文件选择 USB profile 的原接口，但不再修改 HTTP 配置，
显式 NCM profile 可在没有 UCI 的 initramfs 中使用。

用户明确授权后，仅重写 Linux A 的 boot、vendor_boot 和 misc 的 32 字节
临时启动记录；写前/写后校验，使用已有电脑及设备暂存原件作恢复来源。
不刷 Android B、init_boot、dtbo、GPT、userdata 或 NV 分区。
内核包装镜像 SHA-256 全程保持
`1363c4dbad3ad225d8fcac8be9115e9729f3cb70c7a7649466027aa2cc12c226`。

新实机日志明确显示：`stage=wait-storage` 之后才出现 MMC 识别和分区枚举，
然后 `storage-ready → mount-root → switch-root`。根位于 mmcblk0p84，
按 MU300 容器规则读写挂载；USB NCM、ACM、SSH 恢复。用户确认画面与触摸正常。
这是本轮启动修复的一次实机通过，不代表蜂窝、Wi-Fi、充电等全部功能已验收；
本轮只读状态里 WAN 仍报告 ATTACH_FAILED，留待后续适配分析。

## 防止后续打包遗漏

`canonical_boot()` 必须收入 `etc/u30pro-boot-wait.sh`。包内四种槽位/安装模式
smoke 还要核对该文件与源码一致。旧 preview1 仍保留供溯源，不能再次原样安装
后宣称包含此修复。离线 `tools/u30pro-boot-repair.py` 可从已校验的安装事务构造
本机专用两镜像修补，不连接或写设备，不包含固定 LBA、用户 NV 或身份数据。

回归覆盖延迟出现节点、就绪零延迟、缺失根、无 UCI 的 USB configfs 启动、
主备槽方向、分层 LZ4/CPIO、内核/DTB/Android 原件保留及损坏备份拒绝。
