# Installer protocol and recovery contract

The canonical implementation is `e5-linux/installer`. `sync.py <mu300-repository>` generates the other repository's mirror and `SHARED-SOURCE.json`. Edit the canonical source, synchronize, and run `--check`. Do not independently maintain two frontends/state machines. Both builds use the same Tauri executable and backend; repository-specific behavior is in `backend/adapter.py` and the existing Python/device scripts.

Protocol 1: one JSON object per line on stdin/stdout. A request is `{"protocol":1,"id":1,"command":"hello","params":{}}`. Responses contain the same `id`, `type:"response"` and `data:{ok,result}` or `{ok:false,error}`. Events use `type:"transaction"`, `"transfer"`, `"log"`. No terminal-text matching. Legacy stdout/stderr becomes sanitized diagnostic log events, independently of named state/effect callbacks.

`probe` and `plan` accept `choices.method: "uninstall"` (the probe uses its existing `method` parameter). Removal applies only to a verified internal `e5root`/`mu300root` partition. Matching original installation journals and checksummed GPT backups take priority; they prove shrink reversal versus original unallocated-space installation. Without a usable original record, the backend verifies current GPT copies, Linux partition type/identity/alignment, exact kernel node geometry, idle/unmapped state, installed opposite boot/ramdisk route, clean ext4 metadata and the family's fixed installation markers. A bounded host reader reads metadata only: no filesystem mount, helper executable or repair is run. A partition name or boot command line alone is insufficient. Unverified/ambiguous evidence and conflicting valid originals stop before writes. The frontend cannot supply GPT snapshots or command text.

Plans record `previous_android_bytes`, `android_bytes`, `openwrt_bytes`, `reclaimed_bytes`, `released_unallocated_bytes`, `wipe`, `layout_source` (`original_record` or `device`) and nullable `source_transaction`. Device-based plans do not reconstruct historical capacity: if the known root starts at userdata end + 1, only that root's range can enlarge userdata, ending exactly at the current root end. A nonadjacent root becomes unallocated without resizing Android. Unlisted gaps, trailing space and unrelated entries are never merged. The UI explains this rule and displays both returned-to-Android and released-unallocated capacity.

Removal uses the existing `start` confirmation, device mutex, backup transport, cancel boundary, journal export/import and `resume`/`retry` commands. A new removal transaction is always required even when no old installation transaction exists. Snapshots are persisted under its `uninstall/` directory before boot writes. A one-shot ramdisk overlay retains the packaged kernel and board driver initialization, then runs the shared offline worker before root mounting/install/update. It checks both GPT copies against the recorded before/after bytes, commits backup first with flush/readback, copies the running Android slot's boot to the inactive slot and selects Android. Userdata enlargement uses the preservation/reset policy below; release-only removal neither resizes nor resets userdata. `uninstall_armed` warns that pausing the computer cannot withdraw an already staged device action.

Stages include `uninstall_prepare`, `uninstall_offline`, existing Android setup/debugging/root waits, `verify_android` and optional `uninstall_restore_boot`. Waiting has no initialization deadline. Completed GPT restoration never re-arms reset on reconnect/restart. Interrupted boot staging is resumed only after exact GPT/misc/Android readback; unknown layouts and partial GPT mismatches stop for offline recovery. A staged `openwrt.uninstall=1` boot marker and local unfinished journals block new installation/trial plans, including after the computer record is lost. Temporary-boot recognition also rejects this marker. Final completion verifies the restored GPT, absence of the OpenWrt partition, Android filesystem/mapping capacity, consumed recovery request and Android boot selection. `result.uninstalled` distinguishes removal from OpenWrt install/update results; diagnostics include `android_capacity_check`.

On a paused uninstall, `resume`/`retry` optionally accept an explicitly selected `serial` if the ADB endpoint changed. The new connection must already have Android debugging/root ready and match the original CID, profile and planned Android slot. The coordinator acquires CID/serial ownership before its read-only probe, saves only the transport change and retains the original boot/layout evidence. Connection history uses nested `serial` fields and is redacted from public snapshots. No automatic rebinding or device writes occur during this selection. Imported uninstall snapshots are also revalidated semantically: recomputing checksums cannot authorize changes to NV/unrelated entries, a different root range or suppressing a required reset.

Commands are allowlisted in both Rust and Python: hello, snapshot, list, package, devices, adb_connect, adb_disconnect, probe, probe_update, plan, start, resume, retry, cancel, can_close, export, import, diagnostics, verify_openwrt. There is no shell/exec command. A frontend-selected serial is checked against an actual device. All device ADB operations use that serial; eMMC CID and profile are rechecked after reset. SSH maintenance binds the key fingerprint between planning and execution; final verification binds the hardware CID. A plan cannot become executable without `confirmed:true` on its persisted transaction ID.

`adb_connect` accepts one validated `address` (IPv4, hostname or bracketed IPv6, optional port defaulting to 5555). It invokes only the host ADB connect service, then enumerates devices; readiness comes from that list, never connect-output text. The result contains `endpoint`, `state` and `devices` (with a `wireless` flag). No package verification is needed. During an installation, connection is allowed only at safe Android setup/authorization waits and cannot rebind the transaction. `adb_disconnect` requires an exact observed wireless `serial`, returns the remaining devices, and is rejected while a worker is active. It also acquires the shared serial device mutex, so another installer cannot disconnect a transport in use. It cannot disconnect USB devices or all devices. Neither command enables debugging, runs a device shell, pairs Android, restarts ADB or changes network adapters/routes.

`verify_openwrt` accepts only the active transaction ID, a management host and in-memory SSH password during safe `openwrt_boot` waiting. It queues an endpoint change/boot acknowledgement for the existing worker and wakes its retry loop; it cannot mark a transaction completed or execute an installation. The worker persists the endpoint and boot acknowledgement, never the password. Details include `reboot_manually`, `boot_confirmed`, `host` and optional `verification_error`. Manual paths wait for user action; automatic reboot paths identify that request. Wrong CID and SSH authentication/connection errors remain editable waits. Actual filesystem-capacity failure remains a failure and cannot be bypassed with confirmation.

Transactions include format/version, device identity/profile/original slot/storage geometry, selected method/allocation, original partition layout, content-based payload identity, backups, legacy transaction path, completed effects, started/done mutation ledger, current stage/status and final measured result. Writes use flush/fsync plus atomic replacement. Per-CID and per-serial OS locks are shared between repositories. Kernel-released locks survive abnormal process termination correctly. Device scripts retain their own upgrade/partition locks.

Each saved checkpoint increments `revision`. The UI ignores older snapshots for the same transaction, including a request response delivered after a newer event. Existing version-1 records without a revision acquire one on their next save. An unconfirmed saved plan opens its review/confirmation screen; it cannot be resumed as an authorized installation.

Stage timing uses persisted `stage_started_at` and terminal `stage_finished_at` timestamps. Repeated waiting/error snapshots within a phase keep its start time; completed, failed and cancelled states freeze it. Retrying starts a new execution segment. Completion retains the preceding verification phase start. The UI stops its interval on terminal states and renders saved times rather than counting after completion.

Update execution captures the actual SSH runtime's boot UUID in `update_boot_id` before uploading/writing. A completed `update-commit` is a final commit checkpoint: restart goes directly to verification and never repeats the update. The UI announces the automatic restart immediately after commit. Verification requires the bound CID, a valid boot UUID different from the captured one, and measured capacity. A responsive pre-reboot runtime remains a wait; explicit user boot confirmation does not bypass the UUID check. Missing evidence in older update records stops for manual review.

Expected SSH transport loss during the final wait emits `details.connection_state:"reconnecting"` with no `verification_error`. Automatic restart paths stay `waiting_device`; a manually initiated boot retains its pending user action if necessary. Connection refusals/timeouts, absent network interfaces, EOF and SSH banner loss are logged at DEBUG, not presented as warnings or failures. Retry has no overall deadline. Actual authentication failure and a proven wrong CID retain actionable errors and endpoint correction.

Restarting during `openwrt_boot` or `verify_capacity` returns directly to SSH hardware/capacity verification. The coordinator also recognizes final verified commit effects before rechecking an obsolete initial Android plan. A stage-one boot effect, partial/started write or root-only E5 TF write is insufficient; legacy preparation records still require their token/geometry-aware resume path.

Statuses: ready, running, waiting_user, waiting_device, failed, cancelled (a resumable pause), completed. Stages are independent of frontend navigation. Waiting for Android initialization, ADB authorization or root has no transaction deadline. Expected reboot is checkpointed before the reboot command. Every write has a stored intent and a completion checkpoint; completed effects are skipped. Uncertain nonrepeatable writes stop for readback/recovery. Existing backend transaction/geometry/token checks remain authoritative during stage-two resume.

Safety boundaries are before effects and between verified transfer chunks. Cancellation is requested, not process termination. Close is blocked for active operations; the user first requests a pause. If the host disappears during an unsafe operation, the ledger retains the incomplete intent. Reconnecting is not permission to repeat GPT shrink/format. Backups must be exported before reinstalling Windows or deleting app data. Device-only recovery with insufficient identity/layout/backup evidence is refused.

Transfer events contain `name`, actual acknowledged `bytes`, `total`, and `bytes_per_second`. Check/format/shrink/grow only emit phase and activity. Final verification reads raw ext4 superblock bytes over SSH, checks the expected allocated byte count and running OpenWrt, and reports filesystem bytes separately from partition size. No `od` or SFTP is required by that verification.

`log` events include timestamp, DEBUG/ERROR level, scope, stage and sanitized message. Legacy CLI text is diagnostic output only; no state transition is inferred from it. Command boundaries, output, effect checkpoints, backup/hash results and exception tracebacks persist in `debug.ndjson` with a 4 MiB rotation and one previous file. `diagnostics` returns a bounded redacted sharing report from persisted logs even during an active operation; full logs are included in exported backups. Passwords, wireless keys, hardware identifiers and legacy secrets are masked before disk or UI emission.

Boot/chain backup uses device-side `dd` into a private shell-owned directory under `/data/local/tmp/`, then ordinary serial-bound `adb pull`. Source, temporary file and computer file SHA-256 must match. The UI observes actual local file growth for byte progress. Per-file staging is deleted in a finally block and the directory is removed on exit. Temporary-space checks run before `dd`; each partition is staged individually. Failed downloads remain `.partial` and cannot replace an existing verified backup. There is no Base64 or compressed-stream backup path or fallback.

Named `activity` events clear completed transfer counters when another operation starts. `firmware_extract` and `firmware_convert` are preparation stages; the latter includes `details.tool`. Converter changes reset phase timing even within the same stage. Allowlisted host converters run with stdin detached, captured stdout/stderr, hidden Windows processes, five-second diagnostic heartbeats, safe cancellation and a 120-second timeout. Source helper scripts explicitly compile with optimization zero so their docstrings and guards survive the sidecar's optimized build. No installation decision is inferred from their terminal text.

Content compatibility binds adapter, profile, root layout, kernel family and critical boot/rootfs/filesystem-tool hashes. Package paths and GUI/host-script versions are not compatibility keys. Package checksums are verified again on resume. This is integrity against corruption and accidental mismatch, not a signed release authenticity mechanism.


## Removal data policy (journal schema 2)

`plan` for `uninstall` first attempts preservation. The current device must explicitly report `ro.crypto.state=unencrypted`, no file/block encryption, and `/data` must resolve directly to the saved userdata node without mapping overhead. A readable ext4/F2FS superblock and stable UUID, verified ARM64 tools and supported one-shot ramdisk are required. `plan.data_action` is `grow-ext4`, `grow-f2fs`, `reset` or `gap`; GPT enlargement alone is no longer interpreted as permission to reset.

When preservation is unavailable, `plan` returns `{confirmation_required:"format_android",reason,reset_token,model,serial_hint}` instead of a transaction. This is a read-only decision response. No record or device write is made. The GUI reports the reason and offers Cancel / Choose format and review plan. To choose format, call `plan` again with the returned `reset_token` at the top level. The token is single-use and bound to freshly read device/layout/encryption/volume evidence in the current backend session. A stale token or a boolean such as `choices.reset_android=true` does not authorize a reset. A successful reset choice creates a ready plan with `wipe=true`; the existing final `start(confirmed=true)` is still required. Cancellation never sends `start`.

Schema 2 persists the data action, reset authorization, filesystem identity and maintenance-tool hashes. Execution rechecks current preservation eligibility and tools. Tool incompatibility, filesystem check errors and short final capacity never fall through to formatting. Shrink-only F2FS `-s` is not used for growth. The offline worker checks the unmounted data first, commits the verified GPT, requires a kernel partition-table reread and verifies the exact restored userdata start/size before growing its partition node, rechecks filesystem identity/capacity and only then restores Android boot. Growth retries check identity and the same worker image and re-arm only misc; they do not replay partition edits or arm Recovery. No artificial progress percentage is reported for fsck/resize.

Unconfirmed schema 1 removal plans must be regenerated. Already armed schema 1 transactions retain the originally confirmed reset/gap contract; no policy is silently changed during resume. Geometry/identity/installation-evidence failures are not eligible for reset fallback. Once offline execution has begun, an error stops that transaction for verification/recovery; it cannot turn a preservation transaction into a reset transaction without a new reviewed operation.

## Removal without the original record (journal schema 3)

Schema 3 extends schema 2 with `installation_evidence`: hashes of the installed boot header, ramdisk, ext4 superblock and exact fixed marker files. Evidence is rechecked before preparing device writes. The reset-choice fingerprint also includes it. E5 requires its internal-root boot route, `etc/e5/part-root` naming this disk and OpenWrt distribution identity. MU300 requires the native `part`/completed `install-part` ramdisk route, container boot selector, `openwrt/etc/mu300/desktop-mode=part` and OpenWrt identity. Prepared roots, unknown boot routes, symlinks, unclean/unsupported ext4 and mounted/mapped roots are rejected. The host reader supports bounded regular files/directories with direct blocks or initialized extents and checks partition/filesystem bounds; it never evaluates their content as code.

On import/restart, before/after snapshots are recomputed from the saved **current** layout using the adjacent-root rule. Hash changes cannot authorize a wider target or alter unrelated entries. Once armed, resume uses the new uninstall record, not any original installation record or deleted root markers. Recovery from an interrupted inactive-boot write still requires exact saved GPT/misc/Android checks; when boot staging alone must be retried, the original Linux boot proof comes from its checksummed **new uninstall backup** while root evidence is checked live. Completed GPT work and formatting are never replayed. If this new record is lost while `openwrt.uninstall=1` is staged, the existing pending-operation guard still stops new plans; absence of an old installation record is not permission to guess an interrupted removal.

`notice` events carry a fixed localized `code` (`mtp_disabled` or `mtp_disable_failed`) and optional device `label`. Only the MU300 adapter enables the Windows wired-ADB MTP workaround for a selected device; enumeration alone, wireless ADB, macOS and the E5 adapter are unchanged. Windows problem code 22 confirms successful disable. A failure only emits a warning and does not stop the original workflow. MTP is never automatically re-enabled.
